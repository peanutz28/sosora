2026-10-17, provisioning/serving session (exact event time not retained)
Issue: Requested 200 GB disk on gpu-h100-sxm.1gpu-16vcpu-200gb, but observed a
120 GB block device and 116G root filesystem, with 98G available before deploy.
This mismatch also recurred on the separate Oct 18 LoRA instance.
Impact: Durable space was insufficient for the chosen model-cache workflow.
Workaround: Put the BF16 model cache in the VM's 99G /dev/shm tmpfs. This consumes
host RAM and is volatile, despite the instance disk being retained.
Suggestion: Validate requested versus delivered disk at provisioning, report the
actual filesystem capacity explicitly, and offer an attached persistent model
volume/cache with a clear sizing check before download.
Evidence: docs/evidence/vllm_2026-10-17/hardware.json;
docs/VLLM_RESULTS.md, Provisioning.

2026-10-17 23:51:19.312609 EDT; restart restored by 2026-10-18 04:14:11 EDT
Issue: Brev verified the serving H100 STOPPED at the first timestamp. The RAM-backed
model cache does not survive stop. On restart, weights had to be restored; the

Impact: Re-downloading weights added startup work and made stop/start less useful

2026-10-17, same vLLM integration session (exact event time not retained)
Issue: First five complete native hero runs applied the bridge closure and isolated
five incidents, but the final model request failed because full route geometry
made the context too large for the configured window. All five remain failures.
